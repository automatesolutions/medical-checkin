Why this exists

Purpose

Give the Medical Unit a single, reliable place to check in wildfire medical resources (ambulances, REMS teams, EMPFs, MEDL, and related positions) and see who is on the incident, where they are assigned, and when they demobilize — without copying rows between Microsoft Forms and Excel, and without storing clinical or patient data.

Field personnel scan an incident QR and each submit one 34-question form for themselves. The tracker stores that response once, groups people under the resource they were ordered on, and lets staff add only the operational facts the form cannot know (Division, Camp, Call Sign, extensions, document status).

What success looks like

Objective

  • Replace the manual Forms-plus-spreadsheet workflow with a GCP-hosted public check-in form and an IAP-protected admin tracker.
  • Enforce one response = one person, safe resource matching (no silent merges), and separate resource vs personnel counts.
  • Calculate Last Work Day and demobilization dates consistently, and surface them on a one-page Glide Path.
  • Keep original answers immutable; store admin corrections as overrides; store document status only (files stay in the Fire email).
  • Protect restricted personal and contractual fields from roster and Glide Path views.
  • Make an incident closable and reusable as a clean package with no leftover people, responses, or ids.

Public form — purpose and how to use

Purpose: Let each person check themselves in from a phone, with no login. One person = one form. They cannot see the roster or anyone else’s answers. No file uploads.

How to use it:

  1. Scan the printed QR (or open the form link). That opens this form — for example Bearclaw Creek, Step 1 of 6.
  2. Read the orange note: check in for yourself only; no patient/clinical data.
  3. Complete all 6 steps (34 questions): order & identity → position → dates → vehicle → home agency → certification.
  4. Tap Submit check-in.
  5. On the confirmation screen, email Contract, Driver’s License, NREMT, State license (and Medical Director letter if Narcotics) to the Fire email shown — do not upload files in the app.

Every ambulance and REMS team member submits separately. A four-person team = four form submissions.

Medical Unit staff

Admin app — purpose and how to use

Purpose: See everyone who checked in, group them under the right resource, add Division / Camp / Call Sign / extensions, fix bad matches, track document status, and see who demobilizes when. Staff never change what the person typed — they only add work details on top.

How to use it (daily):

  1. Open Admin (Google / Cloud IAP in production). Confirm the right incident.
  2. Go to Check-in form → print or share the QR so field people can use the public form.
  3. Roster — people appear under each resource. Filter All / Active / Enroute / Needs Review. Click a row to open the person drawer.
  4. Person drawer — Submitted answers are locked. Ember-bordered fields are what staff may edit (Division, Camp, effective dates, extension, status). Calculated dates and Glide state update live. Document chips cycle status only.
  5. Review queue — if the system cannot safely match a person to a resource, Link them or Create provisional. Nothing merges by itself.
  6. Documents — mark Received / Verified when mail arrives at the Fire email. Files stay in email, not in the app.
  7. Glide Path — see who is leaving soon; print landscape for briefs.
  8. When the incident ends — Close incident (stops the form). Later create a clean incident for the next fire (no old people or ids).
Common confusion

Where is the QR?

The QR is not on the public form. The QR is the door that opens the public form.

QR code lives here

Admin app → Check-in form screen. Staff print it or share the link. Local example: http://localhost:5174/c/bearclaw-creek

After you scan

Phone opens the public form (Medical Check-In → incident name → Step 1 of 6). No QR scanner button appears on that page — you already arrived.

  1. Staff print QR from Admin.
  2. Field person scans with the phone camera.
  3. Phone opens the public form.
  4. Person fills boxes → Continue → … → Submit.

Postgres · RFC model

Data layer

Tables: Incident, Response, ResourceInstance, Person, DocumentStatus, AuditEvent.

Enforced in domain + DB, not only UI:

  1. One Response → one Person. Unique on (incidentId, formsResponseId).
  2. Match key: incident + normalized Resource Order # + Company + Date Assigned. Order # alone is never enough.
  3. 1 match → link. 0 matches → provisional resource. 2+ → Needs Resource Review; no silent merge.
  4. Response.payload is immutable JSONB. Admin writes overrides only. Clearing an override restores submitted values.
  5. Calculated values are never stored: last work day, DMB start, workdays remaining, glide state.
  6. Formula: LWD = FWD + length − 1 + extensionDays; DMB = LWD + 1. Reassignment is metadata only.
  7. Narcotics in Q10 → required Medical Director letter row.
  8. Restricted fields excluded from roster / Glide Path APIs (address, plate, emergency contacts, EERA, medical director, supervisor phone).

Normalize Resource Order # in domain while storing resourceOrderRaw unchanged. Statuses, document states, and glide hex colors follow the README.

Target environment

GCP deployment

  • Project — one GCP project; region set at first deploy (e.g. us-west1).
  • Cloud SQL — private IP; Cloud Run via Unix socket / Cloud SQL connector. No public SQL.
  • Load Balancer + Cloud Armor — rate-limit public POST.
  • IAP — admin Cloud Run (or LB backend). Allowlist Medical Unit Google accounts. API trusts X-Goog-Authenticated-User-Email as AuditEvent.actor.
  • Check-in Cloud Run — unauthenticated; CORS own origin only; no list/export endpoints.
  • IAM — least privilege; no document buckets.
  • CI — Cloud Build on main → migrate → deploy both services.
  • Close / reuse — create incident from a template with empty operational tables; never copy responses.
RFC §9

Automated test suite

Vitest over synthetic fixtures in packages/domain plus API integration against test Postgres:

  • One response → one person
  • Two Ambos, one match → one resource, two people
  • Four REMS, one match → one resource, four people
  • Ambiguous → review, no merge
  • Later rotation, same order # → new instance
  • Admin edit does not mutate Response.payload
  • Date math + glide thresholds (Green 8+, Yellow 4–7, Red 2–3, LWD 1, DMB 0, REVIEW invalid)
  • Separate resource vs personnel counts
  • Narcotics → Med Director letter required
  • No file / upload / public document-link fields in schema or logs
  • Concurrent submit load: no lost rows, duplicate people, or bad merges
  • Close + new incident: no old ids / responses
